# v1.5.0-shadow.10 — saved setup and device binding review

This evaluation prerelease adds an offline workflow for reviewing selected
robot configurations before reusing them. It does not promote or replace the
stable runtime and does not control hardware.

- Read Linux sysfs/udev device identity metadata without opening device nodes.
- Resolve explicitly reviewed camera, serial and CAN roles into new config
  copies. Missing/ambiguous identities and duplicate endpoint assignments fail.
- Capture selected source/configuration/calibration, record an operator's
  reviewed baseline and compare semantic changes separately from renumbering.
- Prepare native saved inputs for Piper deployment/collection, MakerMods Metal,
  Aditya's SO-101 hardware branch, Dons Beast and Cartesian single/dual arms.
- Add distinct source-workspace mappings for Aditya's five-joint trajectory
  input and Dons Beast's Twist bridge with required node-settings evidence.
- Include the CLI, Python metadata exporter, structural JSON schemas, and
  [the complete workflow and recipe guide](../saved-setup-review.md).

Validation: targeted review against pinned public source, TypeScript build,
Python syntax compilation and packaging/asset integrity checks. No local
test suite, ROS/robot execution, installed-bundle trial or GitHub Actions was
run for this release. A build is not functional or physical acceptance.

The observed public Dons Beast YAML has duplicate `low_voltage_threshold`
keys and a watchdog parameter name that differs from the bridge declaration.
The SO-101 hardware source exports position state while its source controller
configuration also lists velocity. The guide exposes these differences; this
release neither chooses a customer's active settings nor fixes their robot
configuration without their selection.

Reports concern saved, self-attested inputs. USB topology identifies a port,
not the physical unit plugged into it; calibration equality also does not
identify a Metal arm. RLSOK sends no hardware commands and installs no live
driver gate. Current customer configuration, missing private interfaces,
physical integration, actual use and acceptance remain separate evidence.

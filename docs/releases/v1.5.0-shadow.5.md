# v1.5.0-shadow.5 — configuration feedback evaluation

This local evaluation prerelease implements specific controller/source-review feedback. It adds a SO-101 controller type-change workflow, three public-source workspace mappings and concrete command-boundary explanations. It does not establish customer use, vendor endorsement or physical robot compatibility.

- `profile prepare-so101-swap` prepares a new YAML copy changing the same `arm_controller` from JTC to JointGroupPositionController with the specified five joints and unchanged gripper configuration. It sends no ROS request and switches no controller.
- `profile compare-controllers` verifies two exports from the same controller source and produces readable before/after controller, action-endpoint and parameter differences. This historical report does not approve anything; the existing Shadow comparison makes the decision under the original approval.
- `parol6-arm`, `kinova-gen3-7dof` and `xarm1s-moveit-arm` source recipes require the specified active controller, claimed interfaces, ordered joints and fresh controller export, along with actual local source/model/settings/candidate inputs. All eight source mappings retain the independent review workspace and zero-dispatch behavior.
- The controller exporter waits within its existing deadline when service readiness precedes per-node discovery. Duplicate nodes/servers still fail. It uses the same three read-only service types and never fabricates an observation.
- A reviewable propulsor patch validates finite controller batches, position limits and smoothing state, plus Dynamixel software command-frame structure and IDs. It is supplied for a separate pinned upstream checkout; it is not silently installed on a robot.
- A runnable synthetic calibration/limits example demonstrates why changing calibration and then revising limits invalidates the old approval. The local evaluator is real; the illustrative limits and trajectory are fixtures, not customer settings.

Read the [feedback guide](../email-feedback-evaluation-20260910.md), [propulsor code review](../pliant-propulsors-review.md), [source workspaces](../source-shadow-workspaces.md) and [installation guide](../fanuc-shadow-self-service.md). The archives contain all linked guides and experimental source; standalone release guides are also provided.

## Focused verification

On 2026-09-10, only affected checks were selected:

- Two TypeScript controller-change tests: exact requested copy behavior and rejection of wrong starting configurations; verified historical comparison, changed plugin/action/parameters, tampering, different sources and reversed timestamps.
- Five source-workspace tests: all source mappings, preserved profile/approval/candidate, refresh drift, ambiguous/wrong receivers, missing inputs, joint order and controller binding validation.
- Six Python exporter tests: bounded discovery waiting, duplicate/deadline rejection, state changes, parameter encoding and the read-only API boundary.
- Thirty pure-Python callback checks passed after applying the published patch to copies of the pinned upstream files with `git apply --check` and `git apply`. No ROS or SDK imports, serial ports or hardware.
- The executable calibration example returned WOULD_ALLOW for baseline and WOULD_BLOCK for changed calibration and changed limits under the original approval, with no dispatch.

The delivery build and packaging compile/package only. The full test suite and GitHub Actions are not run. Stable v1.4.5 remains separate; install this evaluation into a new directory.

The two explicit ROS Jazzy experiments also completed on the existing local installation:

- [SO-101 evidence](../validation/feedback-20260910/so101/summary.json): actual installed controller_manager/plugins on GenericSystem; the same `arm_controller` changed JTC -> JointGroupPositionController, stayed active with the same five position claims, lost its trajectory action, and preserved the active gripper's exported configuration. The unchanged approval produced WOULD_ALLOW -> WOULD_BLOCK, including `fact_mismatch:active-controller` and missing action coverage. No motion command was published.
- [Kinova prototype evidence](../validation/feedback-20260910/kinova/summary.json): the public seven-axis JTC parameters on GenericSystem produced WOULD_ALLOW while active and WOULD_BLOCK after deactivation under the original approval. The Kortex hardware driver was never loaded; simple fixture links do not represent Gen3 kinematics.

Both directories include actual baseline/changed exports, controller differences and evaluator reports. SHA-256 manifests identify the copied evidence. The original profile/approval/candidate stayed unchanged in both experiments. [Calibration example output](../validation/feedback-20260910/calibration/summary.json) is explicitly synthetic.

Development attempts exposed an experimental missing manager argument, the exporter discovery race described above, and a stale `ros2 param` CLI node view after unload. The experiment now uses its own rclpy node for the mock manager's type change. These failures were fixed before the successful recorded runs; they are not counted as passed checks. The read-only exporter itself still never sets parameters or switches controllers.

## Interpretation

Shadow is a parallel local evaluator. It is not inserted into Kortex `write()` or PAROL6's TCP transport. Direct trajectory topics, alternate controllers, Kortex API clients, gripper, CAN/serial bypasses and physical calibration need separately defined boundaries. Source hashes do not attest running binaries, remote peers, ECU firmware or device behavior. See the guide's architecture diagrams and exclusions.

PAROL6 and xArm mappings are source/preparation validation, not executions of their physical drivers. The hexapod upgrade's actual branch/configuration, alternative ODrive transport and other private customer facts remain to be supplied. No completed customer trial or acceptance is claimed.

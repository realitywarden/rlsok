# v1.5.0-shadow.4 — source workspaces and active controller comparisons

This evaluation prerelease prepares a separate local review workspace from five inspected public ROS 2 source layouts. For SO-101 and TRIK it also requires a read-only export of the selected running controller, so a copied YAML file cannot stand in for an actual controller binding.

- `profile source-recipes` lists the pinned source, files and command boundary for hexapod gait input, SO-101 arm trajectories, TRIK differential drive, the LelyRobot Python bridge and the autonomous rover's Gazebo bridge. `prepare-source` uses actual supplied source files, an expanded URDF, operator settings, a discovered interface and a reviewed local command example. It writes neither an approval nor a fabricated observation.
- `profile export-controller` reads controller-manager state, claimed interfaces, declared parameters and the selected node's action endpoints. It uses only ListControllers, ListParameters, GetParameters and graph queries. It sends no motion command and never switches controllers or changes parameters.
- Initial SO-101/TRIK preparation requires a fresh, active controller with the mapped type and joint interfaces; SO-101 also checks that its controller node hosts the trajectory action. `refresh-source` accepts a later inactive, absent or changed binding from the same source and preserves the original approval, profile, sample and export timestamp. Reports identify the changed `active-controller` fact.
- Discovery excludes action feedback/status transport topics from ordinary message inputs. A successful graph query that finds the selected endpoint absent now records missing coverage for a blocked evaluation. Query failures still stop collection without inventing observations.
- ROS parameter values retain their types, int64 values, and optional-limit defaults such as `inf`, `-inf`, `nan` and unset values in portable JSON. This does not relax finite-number validation for command examples.

Read the [source workspace guide](../source-shadow-workspaces.md), [first-evaluation guide](../local-shadow-first-evaluation.md) and [installation guide](../fanuc-shadow-self-service.md). The release includes a standalone SOURCE-WORKSPACES.md; the package and source archives contain all linked guides.

## Focused validation

Windows and the existing local Ubuntu 24.04 / ROS Jazzy environment, 2026-09-08:

- Five tests in `tests/composable-shadow/source-workspace.test.ts` passed. They cover all five recipe mappings, unchanged approvals after refresh, bad/ambiguous receiver selection, missing inputs, changed profiles, SO-101 joint order, and missing/inactive/wrong/stale/tampered controller exports.
- Thirteen Python tests passed: six topic collector tests, five controller exporter tests, and two affected collector cases. They cover recursive message fingerprints, action transport exclusion, missing endpoints, actual file reads, typed parameter values, changed/duplicate controller state, export failures and the restricted ROS API usage.
- The 27 selected public source files were checked against their pinned Git blob identities. Source preparation uses these layouts without modifying or executing an upstream launch file.
- The public hexapod `GaitNode` ran in an isolated ROS domain waiting for robot_description. Actual graph/file capture gave WOULD_ALLOW at baseline and WOULD_BLOCK after the operator settings changed. No robot description or velocity command was published; the gait timer, Gazebo dynamics and downstream joint motion were not exercised.
- SO-101's public five-joint controller parameters were exercised using the installed ROS controller_manager and JointTrajectoryController with `mock_components/GenericSystem`. The selected arm controller was initially active. After deactivating it and activating a replacement on the same five joint interfaces, the unchanged approval produced WOULD_BLOCK with `fact_mismatch:active-controller`; baseline was WOULD_ALLOW. The replacement's active state and claimed interfaces were read back. No trajectory or velocity command was published.
- TRIK's public DiffDriveController parameters and `/cmd_vel` remapping were exercised with the same installed controller manager and mock hardware, in a separate isolated ROS domain. Deactivating the original controller and activating a replacement on the same two wheel velocity interfaces likewise changed WOULD_ALLOW to WOULD_BLOCK with `fact_mismatch:active-controller`. The approval/profile/example stayed unchanged. The TCP brick driver was not loaded and no velocity command was published.

The real-controller check exposed two exporter issues during development: a mismatched rclpy executor context and rejection of legitimate infinite controller defaults. Both were corrected before the successful SO-101 run. Earlier unsuccessful graph-discovery attempts are not counted as passed validation.

The delivery build and packaging command compile and package without running the full test suite or GitHub Actions. No new ROS environment was installed. There is no claim of a full test suite, Humble compatibility, installed-bundle acceptance, customer environment operation, Gazebo dynamics, LeRobot serial integration or physical robot validation. LelyRobot and rover coverage is source/mapping validation, not execution of their serial or Gazebo bridge hardware paths.

## Interpretation and delivery limits

These are public-source mappings and local software observations, not customer case studies or endorsements. Actual customer versions, launch overrides, controller choices and acceptance remain separate. A source commit in a recipe identifies the mapping reference, not a deployed customer's revision.

The read-only export is a bounded sequence, not an atomic authenticated hardware snapshot. It checks controller metadata before and after parameter reads and rejects detected changes. It does not authenticate binaries, devices, firmware, physical calibration or future execution. Local files and settings remain operator-provided records. Re-export before every capture; an old file does not gain a new observation timestamp by being copied.

WOULD_ALLOW means the declared local checks passed. It is not a physical safety proof, a controller command or an execution permit. Keep first use isolated from physical hardware. No private files are uploaded by these local commands. Public material and contribution credit require a separate agreement.

Stable Runtime v1.4.5 and Cloud/API/schema remain separate. Install this prerelease in a new evaluation directory. Publication and website deployment establish availability, not customer trial use or acceptance.
